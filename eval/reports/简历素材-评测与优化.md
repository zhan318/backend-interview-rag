# 简历 / 面试素材：后端面经 RAG Agent 的评测体系与检索优化

> 数据截至 2026-11-11，来源：`eval/reports/`（retrieval-report.md / e2e-report.md / answers 存档）

## 一、简历上一段话怎么写（项目描述里评测部分）

> 自建四层 RAG/Agent 评测体系（pytest 137 例 / 检索层 Recall@K 消融 / 生成层 LLM-as-a-Judge / e2e 工具路由 36 例），
> 以消融实验驱动检索优化：换中文 embedding 后同口径 Recall@3 由 4.8% 提升至 57.1%，
> 加 Cross-Encoder 精排后达 71.4%；并用阈值标定把库外问题越界检出从 4/4 降到 0/4。
> Agent 工具路由准确率 97.2%（36 例），答案质量分 90.3%。

## 二、三层评测体系（面试讲"怎么保证效果"）

| 层 | 回答什么 | 方法 | 成本 |
|---|---|---|---|
| 单元测试 | 逻辑对不对 | pytest，15 文件 137 用例（14 个单元 + 1 个接口） | 约 75s |
| 检索层评测 | 检索准不准 | golden 集 25 条，代码算 Recall@K / 命中率，**零 LLM 调用** | 免费、可回归 |
| 生成层评测 | 答得好不好 | LLM-as-a-Judge（指标对齐 RAGAS：faithfulness/relevancy/correctness/hallucination） | 每条 2 次调用 |
| e2e 路由评测 | Agent 该调的工具调了没有 | 进程内直调 Agent.run()，日志捕获工具调用序列 vs 预期，含 not_in_kb 防幻觉项 | 每条 1-3 次调用 |

**为什么分层**：检索差和生成差是两码事，混在一起测无法定位瓶颈。分层后能精确回答
"是没检到（检索层）、检到了没答好（生成层）、还是根本没去检（路由层）"。

## 三、检索优化过程（消融实验，同口径 Recall@3）

以下来自同一次实验（2026-11-27，`eval/eval_ablation.py`），语料、评测集、检索实现完全一致，可直接比较：

| 策略 | Recall@3 | 相对上一层 | 单条延迟 |
|---|---|---|---|
| dense 单路（BGE 中文） | 12/21 = 57.1% | — | ~15ms |
| BM25 单路 | 13/21 = 61.9% | +4.8pp | ~15ms |
| + RRF 融合 | 13/21 = 61.9% | +0.0pp | ~15ms |
| + Cross-Encoder 精排 | **15/21 = 71.4%** | +9.5pp | **~6.4s** |

**三个反直觉结论（面试可讲，比"一路涨"更可信）**：

1. **精排是唯一显著正增益的一层**（+9.5pp，救回 2 条、弄丢 0 条），但单条延迟从 15ms 涨到 6.4s（419 倍）。CPU 环境下它是检索链路的主要成本，也是压测里「10 并发饱和」的根因。
2. **RRF 融合没有带来增益**（61.9% → 61.9%），且融合后 @20 只有 61.9%，低于 BM25 单路的 71.4%。根因是 `fuse_documents(top_n=recall_n)` 的截断：两路各 20 条合并去重后最多 40 条，RRF 排完又被截回 20 条，尾部正确文档被挤出。实测把每路召回放宽到 40 条后，RRF@20 回到 71.4%，证明是截断而非算法问题。当前靠精排从候选中补回，换语料时可能暴露。
3. **阈值 0.2 不影响命中率**（有阈值 71.4%，无阈值也是 71.4%），但它把 `not_in_kb` 越界检出从 **4/4 降到 0/4**。它的定位是防幻觉，不是提精度——这个区分很多项目讲不清。

### 历史基线（仅作方向性参考，不可与上表直接比较）

| 版本 | dense 命中率 | 关键改动 |
|---|---|---|
| v0（2026-09-12） | 4.8%（top-3） | Chroma 内置 all-MiniLM-L6-v2（英文模型），中文 query 语义检索几乎失效，全靠 BM25 字面匹配硬撑 |

⚠️ v0 与上表之间**语料规模、索引实现、检索路径都变过**（v0 时 dense 直接取 top-3，没有宽召回、没有精排，vault 内容也比现在少）。跨版本只能说明优化方向，不能当严格 A/B；严格对照以上表为准。

**技术细节可展开**：BGE 官方最佳实践——query 侧加检索指令前缀 + 向量归一化；
换 embedding 维度变化（384→512）必须全量重建索引（272 文件 / 1349 切片，126s）。

### 上下文压缩：81.7% 的 token 削减，且信息没丢

`eval/reports/context-compression-report.md`（`eval/eval_context_compression.py`，真实调用一次 LLM）：

| 指标 | 数值 |
|---|---|
| 会话规模 | 20 轮 / 45 条消息（含工具调用噪声） |
| 摘要 | 288 字（压缩 40 条消息） |
| 对话 token | **3,737 → 685（-81.7%）** |
| 埋入的关键事实 | **5/5 全部保留**（技术栈 / embedding 选型 / 检索指标 / 学习偏好 / 待办） |
| 单次压缩耗时 | 4.4s（跨过 12 条阈值时一次性，不阻塞主流程） |

**面试可讲的缺陷故事（比"我做了压缩"值钱得多）**：
第一次跑这个实验时 GLM 直接返回 400「messages 参数非法」。根因是摘要器只发了一条
`system` 消息，而 GLM 要求至少一条 `user`；外层 `try/except` 只打 warning 就返回 False，
于是**压缩在生产里从未生效**，却因为静默降级没人发现。更值得说的是为什么测试没抓到：
原用例把 `chat` 整个 mock 掉，只验证「有没有调用」，不验证**消息结构是否符合厂商契约**。
修复是补一条 user 消息 + 一条只断言结构的回归用例；并做了「回退代码 → 用例必红」的有效性验证。

### 过载保护：30 并发 p50 82s → 1.9s

`eval/reports/rerank-overload-report.md`（`eval/eval_rerank_overload.py`，同一批查询、同一并发阶梯）：

| 30 并发 | 未加保护 | 加保护（并发 1） |
|---|---|---|
| p50 | 82.1s | **1.9s** |
| p95 | 134.6s | **3.3s** |
| 吞吐 | 0.22 rps | **5.12 rps** |

做法不是"把线程池调大"，而是给 CPU 密集任务一个**出口**：独立线程池 + 非阻塞信号量，
并发超限立即降级为 RRF 顺序（精度 71.4% → 61.9%），而不是排队把延迟越堆越高。

**并发上限用实验定，不是拍脑袋**：1 / 2 / 4 三档在 30 并发下吞吐为 2.40 / 1.34 / 0.40 rps，
并发越高越慢（torch 单次前向已吃满多核）。这条"越大越慢"的结论本身就是很好的面试素材。

### 索引读写锁：一个"没有变好"的结论，反而更值得讲

`eval/reports/index-lock-report.md`（关闭精排，只压 dense + BM25，隔离变量）：

| 30 并发 | 普通互斥锁 | 读写锁 | 变化 |
|---|---|---|---|
| p50 | 378ms | 424ms | **+12%（变差）** |
| p95 | 696ms | 465ms | **-33%** |
| 吞吐 | 40.5 rps | 59.9 rps | **+48%** |

结论不是"读写锁更快"，而是：**读路径本身是 CPU 密集的（query 编码），并发化只能消除排队，不能减少单请求的 CPU 时间**，所以中位延迟没降。收益落在尾延迟与吞吐。根因定位到 CPU 之后，就没有继续优化——完整链路由 LLM 生成（秒级）主导，检索（几百毫秒）不是瓶颈。

这段的价值在面试里是「**你会验证自己的假设，并且敢承认它错了**」：原本以为是锁把并发串行化了，实测发现不是，于是停手，而不是为了写简历继续堆优化。

## 四、e2e 路由评测的独特点（多数候选人没有的部分）

传统 RAG 评测只测检索准确率；**Agentic RAG 还要测路由准确率**——检索作为工具被模型自主调用，检索再好，模型不调就等于没有。

36 条真机评测（25 条 golden RAG + 11 条功能路由），最终干净环境结果：
- **路由总命中率 97.2%**：工具路由 100%、闲聊不误调 100%、笔记读写 100%、RAG 问题 21/21
- 唯一 MISS：库外实时问题（世界杯冠军）模型自主选择联网搜索而非知识库检索——预期定义过严，实际是合理路由
- 答案质量分 90.3%（白盒判分：correct 31 / partial 3 / 其他 2），剩余扣分来自判分边界与沙盒外部 API 超时
- 端到端耗时 p50 29.7s（检索变准后 Agent 不再反复试错调工具，旧版最多单题调 9 次工具）

**评测体系本身经历三轮迭代，每一轮都修掉一个评测方法论 bug（面试重点素材）**：
1. 第一轮：judge 黑盒判分（只看问答）——抽查 5 条低分 4 条误判（如工具调用成功却被判"没调"）→ 改白盒（喂入日志捕获的工具调用序列）
2. 第二轮：路由数据被历史污染——清理时漏清 SQLite 会话历史，Agent 加载了上一轮对话说"你问过一遍"直接复用旧答案 → 补全会话清理，重跑
3. 第三轮（干净环境）：路由 97.2%、质量分 90.3%，数据可信

**测试基建的实现要点**：不改项目代码，通过 logging.Handler 捕获 agent logger 的工具执行记录；
每条用例独立 session 隔离，跑完自动清理向量记忆、SQLite 会话与测试文件。

## 五、评测发现的真实问题（面试讲"你的系统有什么不足"）

1. **工具调用抑制**：简单知识题模型凭参数知识直接答，绕过 RAG（2/21）——解法方向：prompt 约束 / 工具描述强化 / 检索前置路由
2. **golden 集预期文档标注过窄**：多条问题期望唯一"大杂烩"笔记，检索到的专业笔记内容更对口却判 MISS——71.4% 是保守下界
3. **LLM-as-a-Judge 黑盒偏差**：第一版 judge 看不到工具调用记录，抽查 5 条低分 4 条误判 → 改为白盒（喂入日志捕获的调用序列）
4. **写库行为越界**：库外写作请求触发 write_obsidian_note 直接写盘——产品上应有写前确认机制

主动说出局限 + 给出解法方向，比被面试官挑出来强一个量级。

## 六、可复现命令

```bash
# 检索层（零成本，秒级）
.venv/Scripts/python eval/eval_retrieval.py --k 3
# 检索消融：三组对照一次跑完，拆出 dense/BM25/RRF/精排各自贡献（CPU 约 6 分钟）
.venv/Scripts/python eval/eval_ablation.py
# 上下文压缩：真实调用一次 LLM，产出 token 对比与关键事实保留率（CPU 约 40 秒）
.venv/Scripts/python eval/eval_context_compression.py
# 精排过载 A/B：1/5/10/30 并发 × 保护开/关（CPU 约 8 分钟）
.venv/Scripts/python eval/eval_rerank_overload.py
# 索引读写锁 A/B：关闭精排，只压 dense+BM25（CPU 约 1 分钟）
.venv/Scripts/python eval/eval_index_lock.py
# 生成层（每条 2 次 LLM 调用）
.venv/Scripts/python eval/eval_generation.py --limit 10
# e2e 路由（每条 1-3 次 LLM 调用，约 40 分钟全量）
.venv/Scripts/python eval/eval_e2e.py [--only tool|rag|chat] [--no-judge]
```
